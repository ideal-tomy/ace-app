# ace_app｜イベント運営・通常営業の改善要件

作成日：2026年10月20日  
目的：実際の営業で使って見つかった改善点を整理し、既存アプリの操作や集計を壊さずに追加する。

## 1. 背景・基本方針

- ace_app は実運用で好評だったため、既存の来店登録・注文・伝票・会計の流れを維持しながら使い勝手を高める。
- **イベント運営時**と**通常営業時**で必要な機能を分けて実装する。
- 画面や操作を増やし過ぎず、スマートフォンで少ないタップ数で扱えるようにする。
- 売上・滞在・割引の集計が後から確認できるよう、実績と会計上の調整を区別して記録する。

---

## 2. イベント運営時の追加機能

### E-01｜常設フードメニューの登録と注文（イベント・通常共通）

**現状の困りごと**  
フードは毎回手打ちで注文している。定番メニューはドリンクと同じ要領で選択して伝票に載せられると運用が楽になる。

**実現したいこと**  
フードを一度登録したら常設メニューとして残し、注文時に選ぶだけで伝票に反映させたい。定番はそのまま残し、季節メニュー・追加メニュー・材料切れなどはスマートフォンから自由に出し分けたい。

**要件**

- フードは店舗共通の**常設マスタ**として登録する（イベント・通常営業で共通）。営業日ごとの登録し直しは不要。
- 最低限の登録項目は「メニュー名」「単価」。
- よく使う価格 **300円／400円／500円／900円** を素早く選べる。その他の金額も入力可能にする。
- **同じ名前のフードは二重登録できない**（前後の空白・英字の大小は同一視）。休止中のメニューも同名扱い。
- 「今日は出さない」メニューは**休止**にして注文画面から隠す。再開はスイッチを戻すだけで、登録し直しは不要。
- **単価の変更は、削除してから同じ名前で登録し直す**運用とし、単価の編集機能は設けない。
- フード・ドリンクとも、登録・休止・削除はログイン済みのスタッフ全員がスマートフォンから行える（管理者限定の操作は設けない）。
- 管理画面は「メニュー管理」1画面（`/#/menu-edit`）に統一する。登録は「フード／ドリンク → カテゴリ（ドリンクのみ）→ メニュー名 → 金額」の順に進み、完了後に「続けて登録」か「終了（ホームへ戻る）」を選ぶ。
- 登録した商品は、既存のドリンク注文と同じ操作感で選択できる。
- 手打ちでのフード追加（登録していないメニュー）も引き続き使える。
- 注文したフードは数量と単価を含めて該当者の伝票へ追加し、会計金額へ反映する。
- 注文の追加・数量変更・取り消しは既存の注文操作に合わせる。
- メニューの休止・削除を行っても、**確定済みの注文・会計履歴の単価が後から変わらない**ようにする（明細は注文時の名前・単価を保存）。
- 集計では、明細カテゴリ（常設 `FOOD`／手打ち `FOOD_DAILY`）でフード売上をドリンク売上と区別できるようにする。

**画面イメージ**  
ホームまたは注文画面から「メニュー管理」を開いて登録・休止・削除 → 注文画面で「ドリンク／フード」を切り替え → フードをタップ → 伝票へ追加。

**完了条件**  
定番フードを一度登録すれば翌日以降もそのまま注文でき、休止・追加・削除をスマートフォンから行え、顧客ごとの伝票追加から会計まで一貫して利用できる。

### E-02｜名前検索欄の一括クリア

**現状の困りごと**  
検索文字を消す際、スマートフォンの削除キーを何度も押さなければならない。

**要件**

- 名前検索の入力欄の**右端に「×」ボタン**を配置する。
- 文字が入力されているときだけ「×」を表示する。
- 「×」の1タップで検索文字列をすべて削除し、検索結果を未入力時の状態へ戻す。
- クリア後も検索欄への入力をすぐ再開できるようにする。
- ボタンが小さすぎず、スマートフォンで誤操作しにくいタップ領域を確保する。

**完了条件**  
何文字入力していても1タップで全削除でき、次の名前を続けて検索できる。

**実装メモ**  
共通部品 `SearchClearField` をホームの未会計検索と来店者選択の検索に使用。クリア後は検索欄にフォーカスが戻る。

## 3. 通常営業時の追加機能

### N-01｜会計対象時間の手動調整

**現状の困りごと**  
時間制の営業で、5分程度の超過をサービスしたり、状況によって**30分相当の600円**を引いたりする。自動計算だけでは現場の判断を反映しにくい。

**実現したいこと**  
自動計算された時間を参考にしつつ、スタッフが**「何時間・何分ぶんの会計にするか」**を確定できるようにしたい。

**要件**

- 現在の入店・退店時刻に基づく自動計算は維持する。
- 会計画面に「会計対象時間を調整」という操作を設ける。
- 30分単位など、**現在の時間料金の単位に合わせて**請求対象時間を手動で指定できる。
- 例：本来の計算が2時間30分相当でも、2時間として会計できる。この場合、差額の目安は**600円**（現行の時間料金が該当する場合）。
- 調整前の金額／調整後の金額／差額が会計確定前にわかる。
- 誤操作を防ぐため「自動計算に戻す」を用意する。
- **実際の滞在時間**と**会計対象時間**は別項目で保存する。実際の滞在記録を書き換えて割引を表現しない。
- 会計集計では、最終請求額に加えて、時間調整により減額した金額と調整の有無を確認できるようにする。
- ドリンク・フードなど他の注文額は、時間調整の操作によって変わらないようにする。

**画面イメージ**

> 実際の滞在：2時間05分  
> 自動計算：2時間30分／○○円  
> 会計対象時間：**2時間00分**［変更］  
> 時間調整：**−600円**  
> 最終会計：○○円

※自動計算の端数処理、料金単位、時間料金の適用範囲は**既存仕様を調べてから**合わせる。ここで新たな料金ルールを推定して導入しない。

**完了条件**  
5分程度の超過をサービスした場合でも、会計対象時間を手動指定し、正しい請求額・時間実績・調整額を後から確認できる。

**実装メモ**  
- 会計画面（通常営業・未会計）に「実際の滞在／自動計算／会計対象時間［変更］／時間調整」を表示。選択肢は60分から自動計算の請求時間まで30分刻み（減額のみ）。
- 指定中の値は伝票の `billingBilledMinutes` に保存。会計確定時に `billingBilledMinutesFinal`・`timeChargeAutoFinal`・`timeChargeAdjustmentAmount`・`actualStayMinutesFinal`・`departedAt` を保存する。
- 会計確定・時間調整は会計権限を持つスタッフ全員が行える。日別売上の一覧に「時間調整 −○○円」を表示。

### N-02｜退店時刻の事後修正

**現状の困りごと**  
実際の会計は済んでいても、アプリ上の退店処理を忘れることがある。その場合、後から正しい退店時刻に修正したい。

**要件**

- 対象の来店履歴から、退店時刻を後から編集できるようにする。
- 会計済みであっても、必要な権限を持つスタッフが退店時刻を訂正できる。
- 入店時刻より前の時刻など、矛盾した入力を防ぐ。
- 修正すると、**実際の滞在時間**は訂正後の時刻に基づいて更新する。
- **確定済みの請求額・会計対象時間は自動変更しない。** 金額まで修正する場合は、明示的な確認と既存の訂正手順に従う。
- 変更前・変更後の退店時刻と変更日時を記録し、後から経緯を確認できるようにする。
- 会計と退店の状態が不一致でも、売上の二重計上や来店履歴の重複作成が発生しないようにする。

**完了条件**  
アプリ側の退店操作を忘れても、翌日などに来店履歴から正しい退店時刻へ直せて、すでに確定した会計金額は保持される。

**実装メモ**  
- 日別売上集計の会計済み一覧から伝票をタップ →「退店時刻を修正」。入店より前・未来の時刻は不可。
- 更新できるのは `departedAt` のみ（Firestore ルールで金額・会計対象時間・会計時刻の変更を禁止）。修正履歴は `checks/{id}/visit_corrections` に変更前・変更後・日時・修正者を記録。
- 日次締め済みのスナップショット（`daily_closings`）は変更しないため、締め済みの売上・CSV は変わらない。

### UI改善（メニュー管理・一覧・伝票）

**実装メモ**  
- ドリンクの登録・削除は「種類 → サイズ（通常／メガ）→ 名前 → 金額」の段階で進める。メガは保存時に名前の先頭へ「メガ」を自動で付け、通常サイズだけ登録済みの名前を候補に出す。
- データ上は通常とメガが別カテゴリ（例：`TEA_HAI` と `TEA_HAI_メガサイズ`）のままだが、一覧では1つの種類にまとめ、1行に通常・メガの金額と休止・削除を並べる。
- 同じカテゴリに同名のドリンクは登録できない（休止中も含む）。
- 注文画面の手入力ボタンは「その他フード」「グッズ販売」、対象者の切り替えは「伝票切り替え」に統一。
- ホームの未会計カードはバッジを左上にはみ出し、左に名前・人数と金額、中央に滞在時間（上）と入店時刻（下）を同じ字サイズでペア表示。滞在は「経過」なし、1秒ごとに更新（1時間未満は分秒表示）。
- メニュー登録のサイズは「通常」「メガ」＋「通常＋メガ」（2件まとめて登録）。一覧はカテゴリごとのアコーディオン（初期は閉じる）。
- 伝票・明細画面は注文明細をボトムシートではなく画面内に常時表示する。

## 4. データと集計の設計で特に重要な点

| 項目 | 記録する内容 | 意味 |
|---|---|---|
| 入店時刻 | 実際の入店日時 | 滞在記録の起点 |
| 退店時刻 | 実際の退店日時（事後訂正可能） | 滞在実績 |
| 実際の滞在時間 | 入店〜退店から計算 | 利用実績の分析用 |
| 会計対象時間 | 実際に請求した時間 | 時間料金の計算用 |
| 時間料金の調整額 | 自動計算と確定金額の差 | サービス・減額の把握 |
| フード注文 | 商品名・注文時単価・数量・金額 | イベントの注文・売上 |
| 会計確定額 | 最終的に請求した金額 | 売上集計の基準 |

**原則：滞在の事実、会計の判断、確定した売上を混同しない。**

例えば、実際には2時間05分滞在した人について2時間分を請求した場合、滞在実績は2時間05分、会計対象時間は2時間として保存する。後から退店時刻を訂正しても、確定済みの会計結果を勝手に再計算しない。

## 5. 実装時の確認・依頼事項（Codex／開発者向け）

1. **まず既存コードを確認**する。イベント／通常営業の画面分岐、注文追加、伝票計算、料金計算、会計確定、来店履歴、売上集計の現行実装を把握する。
2. **既存の注文・会計ロジックを再利用**する。イベントフードのために別系統の伝票・会計処理を新設しない。
3. 実際の滞在時間・会計対象時間・調整額を明確に分離する。現在の保存形式や過去データとの互換性を確認する。
4. **会計済みデータの訂正で売上が二重計上されないこと**を確認する。既存履歴を壊さない。
5. UIはスマートフォン中心。特に名前検索クリアとフード選択は1〜2タップで自然に使えることを重視する。
6. 既存の料金ルール（端数処理、30分料金、課税処理など）はコードから確認し、推測で変更しない。
7. 変更前に影響箇所を説明し、実装後は以下を確認する。
   - 常設フードの登録 → 休止・再開 → 注文 → 伝票 → 会計 → 集計
   - 検索文字の一括クリア → 続けて検索
   - 時間料金の自動計算 → 手動調整 → 確定 → 履歴・集計
   - 会計済み来店の退店時刻修正 → 滞在実績反映 → 会計金額維持
   - 既存のドリンク注文、通常会計、過去履歴が変わらず動作すること

## 6. 対応範囲と進め方

**先に導入しやすい改善**：E-02 名前検索クリア、E-01 常設フード登録・注文。  
**会計・履歴への影響確認が必要な改善**：N-01 会計対象時間調整、N-02 退店時刻の事後修正。

この順序はあくまで実装上の進めやすさの案であり、現場での必要度・優先順位は別途判断する。
